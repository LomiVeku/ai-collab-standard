## 一、这套规范解决什么问题

项目出问题，绝大多数不是因为"不知道怎么做"，而是因为**做过的判断没有被记录下来、做过的好办法没有被固定下来**——于是同一个坑换个项目再踩一次，同一个人换个会话再错一次。

本规范把可迁移的部分（规则、流程、判据、检查表、失败模式类别、协作机制）从具体项目里抽出来，形成一套跨项目共用的底线，让任何新项目在启动当天就继承已有的经验，而不必从零试错。

它只规定"什么必须成立"，不规定"用什么技术实现"——技术选择留给项目，判定标准留给规范。

## 二、十一条铁律

| # | 铁律 | 一句话说明 |
|---|---|---|
| 1 | 独立复核 | 测试者 ≠ 实施者；实施方的自证不构成放行依据 |
| 2 | 双向可判别 | 任何检查都要能被证明"东西坏了它会失败"，否则它只是在打印 PASS |
| 3 | 确定性先行 | 下结论前先排除工具、环境与偶发；先怀疑自己，再怀疑被测物 |
| 4 | 证据优先 | 只认可复核的证据，不认表述的自信度；没有证据等于没做。验收标准须先于测试由决策者确认 |
| 5 | 交付三查 + 哈希锚定 | 资源实测、一致性比对、从交付位复跑（输出落交付目录之外）；产物哈希锚定到构建输出 |
| 6 | 改前备份、改后回读 | 备份须含哈希；任何写操作后必须回读确认已落盘 |
| 7 | 只增不删 | 断言、阈值、历史条目只增不删不降；作废要标注取代关系 |
| 8 | 用户数据只读 | 测试、安装、升级、卸载流程一律不修改或清理用户数据 |
| 9 | 不可逆操作须授权 | 删除、覆盖、清空、改系统配置前须有明确授权，并留下对象清单与哈希 |
| 10 | 假通过必查 | 报"通过"后必须反问：这是不是边界值、默认值、钳制逻辑或断言缺陷造成的 |
| 11 | 判断留痕 | 有分叉的决策必须留下选项、代价、理由与失效条件；没有留痕的判断，下一个会话可以合法推翻 |

> 第 1–10 条约束**做事的方式**，第 11 条约束**记忆的方式**（v1.1 增补）。前十条保证"这一次做对"，第 11 条保证"下一次不必重新试错"。详见 `07-决策档案.md`。
> **新增铁律的门槛**：违反后果必须是**静默失败**（无告警、无人拦、自信度与正确时相同），且能用一句话记住。两条不满足的写成普通条款，不进铁律表——防止铁律被稀释成口号。
> 第 11 条排在末尾，是因为前十条已被跨文档引用，重排会让历史引用失效；**编号不代表优先级**。

**十一条铁律全部为〔R〕级**（红线，不可让路）。铁律与本规范的条目冲突时，以铁律为准；两条铁律相互冲突时，取更严者；铁律与项目适配表冲突时，以更严者为准。

## 三、规则怎么用：分级、让路、优先序（v1.2）

**总原则**：规则的作用是**降低判断成本**，不是**替代判断**。
任何一条规则，如果让人在明显正确的行动前犹豫，先检查是不是用错了场景，再怀疑自己的判断。**规则是替工作服务的，不是工作替规则服务。**

### 3.1 三级

| 级 | 标记 | 含义 | 能否让路 |
|---|---|---|---|
| 红线 | 〔R〕 | 让路会造成不可逆损失、数据失守或证据失真 | **不可让**；违反即事故，不适用"下不为例" |
| 方法 | 〔G〕 | 默认做法，多数场景最优 | **可让**，须同时满足三条件并留痕 |
| 惯例 | 〔P〕 | 习惯做法，成本低、收益轻 | 可自行调整，不必留痕；连续失效即改 |

标记写在条目标题里，如 `**T-01〔R〕｜双向可判别**`。

**未标注的条目一律按〔G〕处理**——不必为了标注通读全文；哪条真用过，下次遇到时顺手补标。标级不是新任务，是使用时的副产品。

### 3.2 让路三条件（同时满足才成立）

1. **目的明确**：说得出这次让路要达成什么，而不是"感觉不方便"；说不出目的，就是不想做，不是让路。
2. **风险可控**：最坏结果可发现、可回退，且**不触及任何〔R〕条目**。
3. **有人知道**：在当批回执或交付记录里写一行——`让路声明：<条款号> / 理由 / 补回方式`。只写"这次跳过"不算。

**单向行使**：只有**实施方**可以提出让路，**复核方**可以否决，但复核方不得要求实施方让路（否则复核会变成减压阀）。一次让路只管当批、不可追溯追认；**同类让路累计 3 次，视为该条款需要修订**，进规则体检。

### 3.3 事实源优先序

同一事实出现在多处且互相矛盾时，按此裁决，**高者胜，低者改**：

```
用户当次指令  >  挂账台账  >  协作规则  >  教训库 / 填坑备忘录  >  交接包与各类快照
```

- 冲突时的动作是**裁决并纠正低者**，不是"以文件为准"地两边都读、两边都对。**"以文件为准"在文件互相矛盾时是失效的**——它只说明"别信记忆"，不说明"信哪个文件"。
- **用户指令的边界**：用户指令可以改变做法，但解除〔R〕须是**明确授权**（点名对象、说清后果），不接受"你看着办"式的推定同意；授权与对象清单一起留痕（铁律 9）。
- **状态不写进规则文件**：规则里出现的版本号、哈希、断言数、内存占用，一律降级为指针（"见台账 / 版本登记"）。写死一次就过期一次，且过期后无人复核。
- 裁决结果若具有长期性（会跨批次、跨会话），写入决策档案（DR）。

### 3.4 停止条件

复核以**"必改项处置完"**为终点，不是以"我放心了"为终点：
第二轮只查改动区与首轮结论；**同一条检查连续两轮无新信息，即为仪式，就地停止**。
曾经失败过、曾经漏检过的检查**永久不可让路**——它们是被现实标过的〔R〕。

## 五、三种使用场景

**场景 A｜新项目启动**（一次性，约半日）。填完适配表 → 划出红线区 → 定版本制度与门禁命令 → 建填坑备忘录骨架 → **建决策档案骨架（`docs/决策记录.md` + 索引表 + 模板）** → 把本规范与适配表放进项目根目录，声明为必读。此后所有会话的冷启动清单只带这两份文件的路径，不带历史对话。

**场景 B｜日常迭代**。任务书四要素（C-01）→ 实施 → 自检与对照验证（T1/T2）→ 逐条回执（C-08）→ 独立复核（C-15）→ 写入版本登记 → **有分叉的判断当场写入决策档案（DR-01/DR-11）**。中途发现范围外问题只报不改（C-03）。

**场景 C｜交付发布**。交付三查（D-06）→ 跑体检脚本，按退出码判定（D-08/D-09）→ 旧版先归档（D-18）→ 更新版本登记表（D-19）。门禁不过不放行，PARTIAL 不放行。

## 六、效力说明

本规范是**通用底线**，不是建议集合。项目可以在《项目适配表》中**加严**（提高阈值、增加检查、缩短周期），**不得放宽**；确需放宽的，必须在适配表的"偏离登记"里写明条款号、理由、风险承担人与复核日期，否则视为违规。

**偏离 ≠ 让路**：偏离是长期放宽、须登记并经决策者批准；让路是单批次、当批说明、自动失效（§3.2）。用让路替代偏离，等于把长期放宽伪装成临时权宜——这是唯一被明确禁止的用法。

规范与项目本地规则并存时，取更严者执行；两者无法比较严宽时，以能给出更明确"做到/没做到"口径的那条为准。

**部分不适用**：若某章确实不适用于某项目，可在适配表声明"第 X 章不适用"并写明理由，其余章节仍然生效。不允许因为一章不适用就整份弃用。
