## DR-001｜T6 管道 0ms 重连：双层修 + 残余登记为已知限制

- **决策日**：2026-10-19
- **状态**：有效（限制保留）
- **决策人**：DeepSeek（终审）｜ GLM（实施）
- **背景**：T6 管道服务交付后，客户端断开再立即重连返回 `EINVAL(22)`。GLM 报「0ms/0.2s/2.5s 三档全 OK」，DeepSeek 同进程复测真 0ms 失败。排查发现 `pipeListenLoop` **每次**重建实例都带 `FILE_FLAG_FIRST_PIPE_INSTANCE`，旧实例尚未释放时重建失败，随后进入 30s 重试。
- **选项与代价**：
  - A. 不改，登记已知限制——实现零风险，但桌宠若毫秒级重连会不可用；
  - B. 只去掉重建时的 FIRST 标志——消除 EINVAL 主因，但 busy 窗口仍在，断线恢复上限仍是 30s；
  - C. 双层修：首次创建保留 FIRST（防抢注）、循环重建去掉；重试 30s→2s——改动小，恢复上限降到 2s，但仍有毫秒级空档；
  - D. 预创建下一实例 / 多实例管道——能彻底消除，但属架构改动，超出本批。
- **决策**：选 **C**；残余「真 0ms 仍 EINVAL」作为已知限制登记；D 留作后续候选。
- **理由**：B 只解决一层，断线恢复仍可能卡 30s；C 用最小改动把最坏恢复时间压到 2s，且保留防抢注语义；D 没有实际需求证据（桌宠重连通常为秒级），不值得在本批承担架构风险。
- **结果与验证**：终版 exe `94524149…`；≥100ms 可连，真 0ms 仍 `EINVAL`；e2e 九条由专项脚本分别复验通过。注：`py-final.txt` 中 E8/E9/E7 的 `CONNECT-FAIL` 是 E4 断开后未等待 2s 重建的**编排问题**（同一 0ms 限制），不是产品失败，三条已由 `extra-test.py` / `reconnect-test.py` 单独验证。后续受控 A/B（完整会话 / 短连接，各 3 轮）**均 0/3 成功**，双方对差异的归因（GLM「场景不等价」、DeepSeek「进程启动 30–50ms」）都未复现，**机理记为未定论**；结论不变。
- **证据指针**：`_verify/T6-20261019/e2e/reconnect-final.txt`、`scenario-0ms-out.txt`、`output/终审-T6-1.3.0-20261019.md`、`测试流程SOP与填坑备忘录.md` v0.6 §37、`版本登记-内部.md` 1.3.0 行。
- **失效条件**：桌宠侧出现真正的 0ms 级重连需求，或后续改为多实例管道 → 本决策需重评。

## DR-002｜T6/E5：接受「重启换数据」近似 + 单测覆盖进程内路径

- **决策日**：2026-10-19
- **状态**：有效
- **决策人**：DeepSeek（验收口径）｜ GLM（提出近似方案）
- **背景**：任务书 E5 要求「改 `deadline` 为 +3s，到点再收到 `due`，内容为新内容」。进程内改 deadline 需要驱动 UI 或桥接，e2e 工具成本高、易引入新盲区；GLM 采用「重启换数据」近似，并另写单测 `TestDueNewDeadline` 覆盖进程内逻辑。
- **选项与代价**：
  - A. 要求 e2e 必须进程内直达——最贴近真实路径，但需额外驱动 UI/桥，工具复杂度与盲区都上升；
  - B. 接受重启近似 + 单测覆盖进程内路径 + 报告**明确标注「非进程内直达」**——e2e 覆盖面略窄，但逻辑路径有单测，且证据可判别；
  - C. 只跑单测——省成本，但缺端到端整链证据。
- **决策**：选 **B**。
- **理由**：单测覆盖「deadline 变更 → due 计算」的逻辑；e2e 覆盖「载入新数据 → 到点推送」的整链；两者合起来足以支撑验收。关键是**标注近似**，防止把近似当成直达。
- **结果与验证**：GLM 回执已标注「近似路径」；DeepSeek 独立客户端复验 `due.content='新内容B'`（`e5-out.txt`）。
- **证据指针**：`_verify/T6-20261019/e2e/e5-out.txt`、`_verify/T6-20261019/e2e/out/read-E5.txt`（161B，含 `COUNT: lines=2 states=1 dues=0`）、`app-go/pipe_test.go`（`TestDueNewDeadline`）。
- **失效条件**：后续要求 e2e 覆盖进程内 deadline 变更（例如引入 UI 自动化）→ 近似不再够用，需补直达用例。

## DR-003｜T6/E4：证据无效判定 + 我方独立验证，不返工（失败案例）

- **决策日**：2026-10-19
- **状态**：有效
- **被推翻的原判**：GLM 首轮回执把 `CONNECT-FAIL`（17B）当成通过证据，并写成「E4 重连三档 OK」——该原判已推翻，由 SOP v0.6 §38「证据须与命题同向」承接。
- **决策人**：DeepSeek（终审）
- **背景**：E4 的命题是「同一事项继续运行 10 秒，不再收到第二条 `due`」。GLM 首轮 `read-E4.txt` 只有 3 字节 BOM（空文件）；重出后内容为 `CONNECT-FAIL`；回执却分别写成「空」和「E4 重连 0ms/0.2s/2.5s 三档全 OK」——**证据与命题不同向**。
- **选项与代价**：
  - A. 接受「空文件 = 通过」——零成本，但假绿，可能放过重复推送缺陷；
  - B. 要求 GLM 重做 e2e——证据链完整，但重复消耗上下文，且产品行为已可由独立客户端验证；
  - C. 我方独立客户端验证产品行为 + 判 GLM 证据无效 + 报告更正 + 教训入档——证据链由我方补，避免返工，但需自己写客户端。
- **决策**：选 **C**。
- **理由**：产品行为已由 DeepSeek 独立客户端验证（长连接跨 10s，`due` 仅一次）；GLM 的证据不可用是**记录问题**，不是产品问题。重做不会增加新信息，反而消耗一个已经发沉的会话；但必须留痕，防止该文件以后被当成「通过」引用。
- **结果与验证**：`read-E4.txt` 改名 `read-E4-invalid.txt`（作废声明）；GLM 回执两处改正为「E4 = 10s 窗口内 due 仅一次，由 DeepSeek 独立客户端验证」；SOP v0.6 §38 增加「证据须与命题同向」。
- **证据指针**：`_verify/T6-20261019/e2e/out/read-E4-invalid.txt`、`output/终审-T6-1.3.0-20261019.md`、`测试流程SOP与填坑备忘录.md` v0.6 §38。
- **失效条件**：若后续发现 E4 存在真实的重复推送缺陷 → 「产品行为已验证」的结论需重开。
- **备注**：这是「错误决定如何被被发现」的样本——错不在「没有证据」，在**把反向证据当成了正向证据**。

## DR-006｜普适性回流规则：写进通用规范而不是项目内，级标定〔G〕

- **日期**：2026-10-20
- **状态**：有效
- **决策人**：用户（"后续这类对项目运转有明显普适性的修改，都应当考虑同步……这个规则，我们项目内可能不需要，但对普适的规范而言有很强的引导性"）
- **背景**：v1.2 落地后，规范更新仍靠一个假设——主控在主现场，所以看得见哪些经验值得升格。漏洞有三：主控不一定在现场（手感只存在于执行方）、用户不一定想起来（要管的事远多于规范）、漏掉的代价是静默的（无报错，只是经验随会话消失）。06 §6.6 已有四类触发信号，但**没有一类能由项目现场的人发起**。
- **选项与代价**：
  - A. **只写进本项目规则**（如 R0 增一条）——代价：本项目已熟练、用不上；且只解决自己，无法引导其他项目，与用户提出该规则的目的相反。
  - B. **只在 06 §6.6 加第五类触发信号**——代价：只解决了"主控知道有这条通道"，没解决"现场的人知道该提、怎么提"，仍依赖自觉。
  - C. **通用规范内两处：C-19 动作（02）+ §6.8 判据（06）**——代价：v1.2 刚宣称"零新增条文"，此时新增 1 条需自带成本与失效条件，且必须证明它不会变成噪声源。
- **决策**：选 **C**；级标定 **〔G〕**（默认做、做不了当批说明），不标〔R〕也不标〔P〕。
- **理由**：A 是"只利己"；B 有通道无动作，等于把责任又推回给自觉；〔R〕会让"每批都提"变成硬动作，必然产出噪声式提议——**噪声会淹没真信号**；〔P〕可"自行调整"等于可以无视，保不住用户要的引导力。〔G〕的语义正好：默认做，不做要说一声。

## 新条目模板

```markdown
## DR-XXX｜一句话标题

- **决策日**：YYYY-MM-DD（补记须另注记录日）
- **状态**：待验证 / 有效 / 已推翻 / 被取代 → DR-XXX
- **决策人**：谁最终拍板
- **背景**：为什么会走到这个分叉（只写必要事实）
- **选项与代价**：
  - A. ……——代价：……
  - B. ……——代价：……
- **决策**：选了哪个
- **理由**：为什么是它；A / B 在什么条件下会更优，为何当前不成立
- **结果与验证**：实际发生了什么，验证到哪一步
- **证据指针**：命令输出 / 哈希 / 文件路径 / 条款号
- **失效条件**：出现什么情况时重开
```

## 维护规则

1. **只记有分叉的决策**：多方案择一、结论被证伪修正、跨会话会再遇到；同等条件下失败案例优先（规范 DR-01）。
2. **两档入库**：当场写「决策日 / 背景 / 选项与代价 / 决策 / 理由」，状态记 `待验证`；转 `有效` 前补齐决策人、结果与验证、证据指针、失效条件（规范 DR-02）。
3. **决策发生时当场写**：实施方起草「背景 + 选项与代价」，拍板方补「决策 + 理由」，验证后补「结果」；事后补记须标「补记」并另注记录日（规范 DR-08）。
4. **一条不超过一屏**：长分析留在报告里，这里只放结论与指针（同规范 M-02）。
5. **不删除，只改状态**：被推翻的条目保留原判，状态改为「已推翻」并注明原因；被新决策取代的，写「被取代 → DR-XXX」（规范 DR-07 / 01 章 1.6 / M-06）。
6. **编号连续**：`DR-001` 起，按时间递增；不得与交付 `D-xx` 混用（规范 DR-09）。
